## 1. Общие правила

### 1.1. Формат обмена

- Все запросы и ответы — **JSON** (`Content-Type: application/json`), кодировка UTF-8.
- Клиентский API **никогда** не отдаёт техническую информацию о моделях ИИ (имена моделей, ранги каскада) — это принципиальный запрет. Не ждите таких полей и не показывайте их.
- Отсутствующее или `null` поле трактуется как «нет данных».

### 1.2. Заголовки запросов

| Заголовок | Обязателен | Описание |
|---|---|---|
| `Authorization: Bearer <session_token>` | для всех, кроме помеченных «без авторизации» | Токен сессии из `auth/init` |
| `X-App-Version: <versionCode>` | рекомендуется всегда | Целый код версии. Если передан и меньше `min_version_code` — все запросы вернут 426. Не передан / `0` — проверка версии пропускается |

### 1.3. Авторизация

- `401` / `UNAUTHORIZED` — заголовка нет или сессия не найдена. Действие: **перегенерировать сессию через `auth/init`**.
- `401` / `SESSION_EXPIRED` — сессия умерла по неактивности **90 дней**. То же.
- `403` / `ACCOUNT_BANNED` — устройство заблокировано администратором. Показать текст, не ретраить.

> Сессии не «протухают» по времени — только по 90 дням неактивности (продлевается сервером при каждом запросе). Максимум **5 сессий на аккаунт**: создание 6-й удаляет самую старую.

## 2. Глобальные проверки сервера

Выполняются **до** обработки любого эндпоинта. Клиент обязан уметь обрабатывать эти ответы на ЛЮБОМ запросе:

### 2.1. Технические работы (503)

```json
{
  "success": false,
  "error_code": "MAINTENANCE",
  "message": "Технические работы"
}
```

Поле называется `message` (не `error`) — показывайте `message`.

### 2.2. Требуется обновление (426)

Если `X-App-Version` меньше `min_version_code`:

```json
{
  "success": false,
  "error_code": "UPGRADE_REQUIRED",
  "message": "Данная версия приложения больше не поддерживается. Пожалуйста, обновитесь.",
  "update_url": "https://..."
}
```

Показать экран обновления, кнопка → `update_url`. Не ретраить.

### 2.3. Прочее

- `OPTIONS` → `200` с открытыми CORS-заголовками (для нативного клиента прозрачно).
- Некорректный JSON в теле → `400` `{ "error": "Invalid JSON in request body", "error_code": "INVALID_JSON" }`.
- Неизвестный путь → `404` `{ "error": "Endpoint Not Found", "error_code": "ENDPOINT_NOT_FOUND" }`.
- Внутренняя ошибка → `500` `{ "error": "Internal server error", "error_code": "INTERNAL_ERROR" }` (без деталей — детали только в админ-логах).

## 3. Формат ошибок и коды ошибок

Единый формат ошибки:

```json
{
  "error": "Human-readable text (EN) — safe to display as is",
  "error_code": "MACHINE_CODE"
}
```

**Правило:** `error` всегда безопасен для показа; `error_code` — только для ветвления логики, не для показа. Пользовательские ответы ИИ (ассистент `content`, поиск `reply`) формируются **на языке запроса пользователя**.

> **Гарантия (с 17.11.2026):** сервер возвращает явный `error_code` на **любой** ошибке — валидация входа, 404, IDOR, 502 от ИИ, внутренние 500. Клиенту не нужно сопоставлять английские тексты регулярками: сначала смотрим `error_code`, текст — только фолбэк для показа.

- `AI_UNAVAILABLE` — «The AI service is temporarily unavailable. Please try again later.» (для тарифа вообще не нашлось подходящих моделей);
- `AI_OVERLOADED` — «All available AI models are overloaded or returned errors. Please try again in 1-2 minutes.» (модели были, но все упали).

**Квота при 502 не списывается** (списание — строго после успешного вызова модели).

## 4. Модель квот и тарифов (лимиты ИИ)

> Это та самая «настройка лимитов». Значения задаются владельцем в админ-панели (Конфиг → «ИИ-лимиты», тарифы — см. часть II, §27 и §21), а клиент получает готовые цифры с сервера и никогда не хранит их захардкожено.

### 4.1. Три независимые квоты

1. **«Витамины ИИ»** (`monthly_ai_quota`) — месячный счётчик, единая валюта для ВСЕХ ИИ-действий. Списание «весом»: каждое действие стоит N единиц (§4.2). Пользовательское название валюты — «витамины ИИ» (ранее в доках назывались «ИИ-запросы»); **имена полей API не менялись**.
2. **Фото** (`monthly_photo_quota`) — месячный счётчик оцифровок по фото: 1 фото = 1 единица. Текстовая оцифровка фото-квоту не тратит.
3. **Облачные рецепты** (`cloud_recipe_quota`) — НЕ месячный: это общий котёл облачного хранения — облачные рецепты + рецептов в бэкапе суммарно ≤ лимита (§12). Удаление освобождает место.

Месячные счётчики живут по UTC-месяцам (`YYYY-MM`) и обнуляются 1-го числа. Момент обнуления — `/user/status` → `monthly_resets_at` (Unix, секунды, UTC).

### 4.2. Стоимость действий в «витаминах ИИ»

Расценки приходят в поле `ai_costs` (в `/app/config` и `/user/status`):

```json
"ai_costs": {
  "assistant": 1,            // один шаг кухонного ассистента
  "parse": 1,                // оцифровка текстом
  "parse_photo": 2,          // оцифровка по фото
  "search_single_per_60": 1, // множитель обычного поиска (за каждые 60 рецептов)
  "search_finish": 1,        // финиш двухфазного поиска (плоская цена)
  "search_plan": 0           // планирование двухфазного поиска (обычно бесплатно)
}
```

**Цена обычного (одиночного) поиска** зависит от размера переданной библиотеки:

```
weight = max(1, ceil(число_переданных_рецептов / 60)) × search_single_per_60
```

При множителе 1: 0–60 рецептов → 1, 61–120 → 2, 121–180 → 3, 181–240 → 4. `search_single_per_60 = 0` — обычный поиск бесплатный.

Клиент **сам управляет ценой**: сколько рецептов передал в `local_recipes` (до капа 240), столько и оплачивает. Прогноз цены можно показать ДО запроса по этой же формуле.

**Цена двухфазного поиска** = `search_plan` (на plan, если > 0) + `search_finish` (на finish). Дефолт 0 + 1 = **1 «витамин ИИ» всегда**, независимо от размера библиотеки — поэтому двухфазный выгоднее обычного при большой библиотеке.

### 4.3. Как клиент узнаёт остатки

- До запроса: `/user/status` → `quotas.ai_requests.remaining`.
- После платного ИИ-действия: ответ содержит `cost` (списано, в витаминах ИИ) и `remaining_month` (новый остаток) — **обновляйте кэш из этих полей**, без лишнего `/user/status`.
- При `QUOTA_EXCEEDED` текст `error` уже содержит цену действия и остаток.

### 4.4. Поля тарифа, влияющие на поведение клиента

| Поле `/user/status` | Смысл |
|---|---|
| `plan_level`, `plan_name` | Уровень и название тарифа (0 = «Карантин») |
| `subscription_active` | Есть активная платная подписка |
| `is_quarantined` | План 0: все ИИ-функции вернут `FREE_TIER_QUARANTINE` |
| `features.allow_photos` | Можно ли оцифровывать по фото |
| `features.max_agent_depth` | Макс. число tool-раундов ИИ-поиска (1–3, сервер капает) |
| `quotas.cloud.limit` | Лимит облачного хранения: облачные рецепты + бэкап суммарно (0 — недоступно) |

## 5. Системные эндпоинты

### 5.1. `GET /api/v1/app/config` — конфиг приложения (без авторизации)

Первый запрос при старте. Кэшируйте; при офлайне используйте последний успешный ответ.

```json
{
  "min_version_code": 12,
  "latest_version_code": 15,
  "update_url": "https://...",
  "maintenance_active": false,
  "ai_costs": { "...": "см. §4.2" },
  "features": {
    "parse_enabled": true,
    "assistant_enabled": true,
    "ai_search_enabled": true,
    "feedback_enabled": true
  }
}
```

**Клиент:**
- `maintenance_active: true` → можно заранее показать заглушку (сервер всё равно вернёт 503 на каждый запрос).
- `latest_version_code` > текущей версии → предложить «доступно обновление» (не блокируя работу).
- `features.ai_search_enabled = false` → скрыть ИИ-поиск заранее (сервер всё равно вернёт 403 `FEATURE_DISABLED` с текстом «ИИ-поиск временно отключён» — обрабатывайте его на любом случае).

### 5.2. `GET /` или `GET /api/v1` — пинг (без авторизации)

```json
{ "service": "Cookin Backend API", "status": "online", "time": "2026-11-14T..." }
```

## 6. Авторизация и перенос подписки

### 6.1. `POST /api/v1/auth/init` — вход/регистрация по устройству (без авторизации)

Создаёт аккаунт при первом запуске или возвращает существующий по `device_id`. Также используется после `UNAUTHORIZED`/`SESSION_EXPIRED`.

```json
{ "device_id": "уникальный-идентификатор-устройства", "device_info": "Android 14 / Pixel 8" }
```

- `device_id` обязателен, строка. **Никогда не меняйте** между установками — иначе аккаунт (подписка, счётчики, облако) потеряется.
- `device_info` опционален.

**Ответ:**

```json
{
  "success": true,
  "session_token": "hex-64",
  "account_id": "acc_xxxxxxxxxxxx",
  "plan_level": 1,
  "subscription_until": 0
}
```

**Rate limit:** 10 запусков/час и 60/сутки на IP — дёргайте `init` только по событиям (первый старт / 401).

**Ошибки:** `400` (нет device_id), `403 ACCOUNT_BANNED` («Устройство заблокировано»), `429 RATE_LIMITED`.

### 6.2. `POST /api/v1/auth/logout` — выход (авторизация)

Инвалидирует текущий `session_token`. Ответ всегда `{ "success": true }` — даже если токен уже мёртв.

### 6.3. Перенос подписки между устройствами

Сценарий: подписка куплена на телефоне A, переносится на телефон B.

#### `POST /api/v1/auth/transfer/create` (авторизация, устройство-ДОНОР)

Требует активную платную подписку, иначе `400` «На устройстве нет активной платной подписки».

```json
{ "success": true, "transfer_code": "123456", "expires_in_seconds": 600 }
```

Код 6-значный, живёт 10 минут, одноразовый. Новый код **аннулирует** предыдущие неиспользованные коды аккаунта.

#### `POST /api/v1/auth/transfer/claim` (авторизация, устройство-ПРИЁМНИК)

**Тело:** `{ "code": "123456" }`

**Ответ:**

```json
{ "success": true, "plan_level": 2, "subscription_until": 1735689600 }
```

**Проверки по порядку:**

| Ошибка | HTTP | Причина |
|---|---|---|
| `RATE_LIMITED` «Слишком много попыток…» | 429 | > 5 попыток ввода кода в час на аккаунт-приёмник |
| «Неверный, просроченный или уже использованный код» | 400 | кода нет / использован / истёк |
| «Исходный аккаунт не найден» | 400 | внутренняя проблема |
| «Нельзя перенести подписку на то же самое устройство» | 400 | claim с того же аккаунта |
| «Подписка на исходном устройстве уже неактивна» | 400 | донор уже без подписки |
| «Перенос временно заблокирован кулдауном 7 дней» | 429 | с последнего переноса донора < 7 дней |
| «Исчерпан лимит переносов подписки (максимум 2)» | 403 | донор уже переносил дважды |

После успешного claim: донор уходит в **карантин на 30 дней** (план 0), приёмник получает тариф и срок подписки донора. **Месячные счётчики ИИ/фото при этом НЕ переносятся** — приёмник стартует со своими текущими остатками (вместе с подпиской копируется только дневная статистика использования, она на квоты не влияет).

## 8. ИИ: оцифровка рецепта

### 8.1. `POST /api/v1/recipe/parse` (авторизация)

Превращает «сырой» кулинарный текст или фото в структурированный JSON рецепта.

**Тело (достаточно одного из двух; можно оба — тогда модель получит и текст, и картинку, а цена будет как за фото):**

```json
{
  "raw_text": "текст рецепта до 4000 символов",
  "image_base64": "base64 без data:-префикса",
  "mime_type": "image/jpeg"
}
```

**Ограничения:**
- `raw_text` ≤ 4000 символов; пустой текст без фото → `400`.
- Фото: `mime_type` ∈ `image/jpeg | image/png | image/webp | image/heic | image/heif`; base64 ≤ 7 000 000 символов (≈5 МБ бинарно).
- Фото недоступно при `features.allow_photos = false` → `403 PHOTO_RESTRICTED`.

**Ответ:**

```json
{
  "success": true,
  "recipe": { "..." : "см. §14.1 — полная локальная форма рецепта" },
  "cost": 1,
  "remaining_month": 92
}
```

`cost` = `parse` (текст) или `parse_photo` (фото). За запрос с фото списывается **и ИИ-квота, и фото-квота**.

**Важно:** `recipe` — это **сырой JSON модели** (сервер проверил только обязательные `title`/`ingredients`/`steps`). В нём есть и личные/служебные поля (`servings`, `chefHeatingType`, `chefTemperature`, `chefTiming`, `chefReadinessSign`), которых в облачной форме не будет (§14.1) — храните их локально, при upload в облако они вырежутся.

**Ошибки:** `FEATURE_DISABLED`, `FREE_TIER_QUARANTINE`, `UNSUPPORTED_IMAGE` (415), `IMAGE_TOO_LARGE` (413), `PHOTO_RESTRICTED`, `PHOTO_QUOTA_EXCEEDED`, `QUOTA_EXCEEDED`, `502`, `500` «Ошибка парсинга формата рецепта», `422` «ИИ вернул неполную структуру рецепта».

## 9. ИИ: кухонный ассистент

### 9.1. `POST /api/v1/assistant/step` (авторизация)

Пошаговый чат «су-шефа» по текущему блюду. Один вызов = один ответ. Диалог клиент хранит у себя и присылает целиком.

**Тело:**

```json
{
  "messages": [
    { "role": "user", "content": "какая температура духовки?" },
    { "role": "assistant", "content": "..." },
    { "role": "user", "content": "а если без яиц?" }
  ],
  "recipe_context": "Название + краткое описание текущего рецепта (до 800 символов)",
  "allow_recipe_updates": true
}
```

- `messages`: роли `user` | `assistant`, каждое `content` сервер режет до **400 символов** (режьте и вы — так дешевле). История обрезается до `max_history_turns × 2` последних сообщений; начальное assistant-сообщение отбрасывается. После нормализации пусто или последнее не от user → `400`.
- `recipe_context` ≤ 800 символов, опционален.
- `allow_recipe_updates: true` + непустой `recipe_context` включает режим **«разбор полётов»** (propose-патчи, ниже). Без флага ассистент только разговаривает.

**Ответ:**

```json
{
  "reply_type": "text",
  "content": "текст ответа ассистента",
  "proposed_update": null,
  "cost": 1,
  "remaining_month": 91
}
```

**Три случая в ответе:**

1. **`reply_type: "text"`** — обычный ответ, показать `content`.
2. **`reply_type: "tool_call"`** — ассистент прислал команду переключения шага: `content` имеет вид `TOOL: go_to_step | N` (например `TOOL: go_to_step | 3`). Клиент обязан распарсить её и **переключить экран на шаг N**; пользователю текст не показывается. Формат гарантирован сервером (команда нормализуется, где бы модель её ни написала); если модель написала в ответе что-то иное «руками», это приходит обычным `text` без сырых команд.
3. **`proposed_update` не null** — «разбор полётов»: ассистент предлагает правки рецепта (§14.3). Сервер ничего не применяет и не хранит — клиент показывает карточку с diff и применяет патч к локальному рецепту только по подтверждению пользователя. `change_summary` — служебное поле для карточки, в рецепт не писать. Если `content` пуст, а `proposed_update` есть — показывайте `proposed_update.summary`.

**Ошибки:** `FEATURE_DISABLED`, `FREE_TIER_QUARANTINE`, `ASSISTANT_LOCKED`, `QUOTA_EXCEEDED`, `400` (нет сообщений / некорректная история), `502`.

## 10. ИИ-поиск рецептов

Диалоговый поиск «подбери мне что-нибудь»: ищет по локальной библиотеке и/или облачной базе, помнит диалог («нужно слаще», «не это, другое») и не повторяет уже предложенное.

| Flow | Эндпоинт | Когда использовать | Цена |
|---|---|---|---|
| Обычный (одиночный) | `POST /recipes/ai-search` | Библиотека маленькая (≤60–120 рецептов) | `max(1, ceil(N/60)) × search_single_per_60` |
| Двухфазный | `plan` → локальный поиск → `finish` | Библиотека большая | `search_plan` (обычно 0) + `search_finish` (1) |
| Legacy | `POST /recipes/ai-search` | старые клиенты | — |

Все flow возвращают одинаковый формат результата. Доступ: `feature_ai_search_enabled` → `FEATURE_DISABLED`; карантин → `FREE_TIER_QUARANTINE`; квота 0 → `AI_SEARCH_LOCKED`.

**Переключатель режима — на стороне приложения.** Сервер не навязывает и не конфигурирует режим: приложение само решает, каким flow искать, и сообщает тип выбором эндпоинта — `POST /recipes/ai-search` (обычный) или `POST /recipes/ai-search/plan` → `/finish` (двухфазный). Оба режима равноправны на любом тарифе с доступом к ИИ и возвращают одинаковый формат результата, поэтому переключаться можно в любой момент диалога — история `messages` передаётся одинаково. Цены обоих режимов лежат в `ai_costs` (§4.2): прогноз стоимости можно показать прямо на переключателе до запроса.

### 10.1. Обычный поиск: `POST /api/v1/recipes/ai-search` (авторизация)

**Тело:**

```json
{
  "scope": "all",
  "limit": 10,
  "messages": [
    { "role": "user", "content": "хочу что-то малиновое" },
    { "role": "assistant", "content": "..." },
    { "role": "user", "content": "нет, нужно слаще" }
  ],
  "local_recipes": [
    {
      "id": "42",
      "title": "Малиновый пирог",
      "status": "VERIFIED",
      "tags": ["десерт", "выпечка"],
      "minutes": 55,
      "ingredients": "малина, мука, сахар, яйца",
      "cloudId": "rec_8f2a..."
    }
  ]
}
```

- `scope`: `"all"` | `"local"` | `"cloud"` (дефолт `all`). `limit` 1–20, дефолт 10.
- Вместо `messages` можно прислать `"query": "строка"`.
- `messages` обрезаются до `max_history_turns × 2` (дефолт 6 сообщений), `content` ≤ 600 симв. Последнее сообщение **обязано** быть от user → иначе `400`.
- `local_recipes` капается до **240**. Поля: `id` и `title` обязательны; `status` ∈ PLANNED/VERIFIED/NEEDS_WORK/ARCHIVED (NEEDS_WORK — «непроверенные, ИИ предлагает их смелее»); `tags` до 6; `ingredients` ≤ 160 симв.
- `cloudId` передавайте у каждого скачанного из облака рецепта (scope `all`/`cloud`): сервер **жёстко исключит** эти recipe_id из облачной выдачи — «новое и необычное» не предложит то, что уже стоит.

**Ответ:**

```json
{
  "success": true,
  "scope": "all",
  "reply": "Подобрал два слащих малиновых десерта…",
  "results": [
    { "source": "local", "id": "42", "title": "Малиновый пирог", "tags": ["десерт"], "reason": "слаще за счёт сиропа" },
    { "source": "cloud", "id": "rec_8f2a...", "title": "Малиновый чизкейк", "tags": ["десерт"], "minutes": 90, "reason": "…" }
  ],
  "cost": 1,
  "remaining_month": 90
}
```

- `source: "local"` — открыть локальный рецепт по `id`; `source: "cloud"` — `id` это `recipe_id` в облаке (скачать `GET /recipes/{id}`).
- Сервер **гарантирует**, что каждый id существует (локальный — из вашей библиотеки, облачный — из реальной выдачи): модель не может «выдумать» рецепт.
- Облачная выдача включает и **ваши собственные** облачные рецепты (публичные и приватные) — поэтому важно передавать `cloudId`, чтобы установленное не предлагалось как «новое».
- Пустой `results` + осмысленный `reply` — нормальный ответ («ничего не нашлось»), не ошибка.

**Ошибки:** `400`, `QUOTA_EXCEEDED` (в тексте цена и остаток), `502`, общие из §10.

### 10.2. Двухфазный поиск

**Фаза 1 — `POST /api/v1/recipes/ai-search/plan` (авторизация):**

```json
{
  "scope": "all",
  "messages": [ "...тот же формат диалога..." ],
  "cloud_ids": ["rec_abc...", "rec_def..."]
}
```

**Ответ:**

```json
{
  "success": true,
  "search_token": "hex-32",
  "plan": {
    "keywords": ["малина", "десерт", "сироп"],
    "ingredients": ["малина"],
    "min_minutes": null,
    "max_minutes": 90
  },
  "cloud_found": 8,
  "expires_in": 600
}
```

- **Квота не списывается** (при `search_plan = 0`), но rate limit — **20 планов/час**.
- `plan` — что модель извлекла из диалога; удобно показать как «условия поиска» (чипы «малина», «до 90 мин»).
- `cloud_found` — сколько рецептов сервер уже нашёл в облаке (результат хранится в сессии на сервере).
- Сессия: **одна активная на аккаунт** (новый план затирает предыдущий), живёт **10 минут**.
- Ошибки: `RATE_LIMITED` (429), `QUOTA_EXCEEDED` (если `search_plan > 0`), `400`, `502`.

**Фаза 2 (клиентская):** по `plan.keywords` + `plan.ingredients` ищете по локальной базе и отбираете до **30** кандидатов.

**Фаза 3 — `POST /api/v1/recipes/ai-search/finish` (авторизация):**

```json
{
  "search_token": "hex-32",
  "messages": [ "...тот же полный диалог..." ],
  "limit": 10,
  "local_matches": [
    { "id": "42", "title": "Малиновый смузи", "status": "NEEDS_WORK", "minutes": 10, "ingredients": "малина, банан, молоко" }
  ]
}
```

`local_matches` — как `local_recipes`, но без `tags`/`cloudId`; кап 30.

**Ответ** — идентичен ответу обычного поиска. На этом шаге списывается `search_finish`.

**Ошибки сессии:**

| Ошибка | HTTP | Действие клиента |
|---|---|---|
| `SEARCH_SESSION_NOT_FOUND` (раньше `SESSION_NOT_FOUND`) | 404 | перепланировать (новый plan → локальный поиск → finish) |
| `SEARCH_SESSION_EXPIRED` (раньше `SESSION_EXPIRED`) | 410 | то же |

**Правила ретрая (обязательные):**
1. Ретрай ровно **1**, не бесконечный цикл.
2. При ретрее — **заново** локальный поиск по keywords НОВОГО плана.
3. **Дебаунс finish**: каждый успешный finish списывает квоту; защита от двойного тапа/повтора сети — один finish на один план.

### 10.3. Правки пользователя = новый цикл

Диалог передаётся на обоих шагах одинаково (полная история). Правка («нужно слаще») — это **новое user-сообщение и новый план**: `plan` → новый локальный поиск → `finish`. ИИ не повторит уже предложенные рецепты — это учтено промптом.

## 11. Облачные рецепты

Все эндпоинты авторизованы, кроме `public`/`access`. `recipe_id` — строка (клиент генерирует сам, ≤ 100 символов; рекомендация — UUID). `access_code` — 10-значный код без похожих символов (без I, L, O и 0, 1), регистр не важен.

### 11.1. `POST /api/v1/recipes/upload` — загрузка/обновление своего рецепта

```json
{
  "recipe_id": "uuid-строка ≤100 симв.",
  "payload_json": "СТРОКА — JSON-сериализованный рецепт",
  "is_public": false
}
```

**Санитайзер:** сервер прогоняет payload через whitelist (§14.1) — **личные поля вырезаются до записи**. После санитайза рецепт обязан иметь `title` (непустая, ≤200), `ingredients` (1–150), `steps` (1–100) → иначе `422`.

**Ответ:** `{ "success": true, "recipe_id": "...", "access_code": "ABCD234567" }`

- `access_code` выдаётся автоматически и **не меняется** при обновлении/смене видимости.
- Обновление существующего `recipe_id` не расходует лимит; создание нового проверяет `quotas.cloud` — место делят облачные рецепты и бэкап (§12) → `403 CLOUD_QUOTA_EXCEEDED`.
- `403` «Нет доступа к изменению чужого рецепта»; `413` — payload > 200 000 символов.

### 11.2. `POST /api/v1/recipes/visibility` — сменить публичность

**Тело:** `{ "recipe_id": "...", "is_public": true }` (boolean обязателен). Ответ `{ "success": true, "recipe_id": "...", "is_public": true }`. `404` если рецепт не ваш/не найден.

### 11.3. `GET /api/v1/recipes` — список своих облачных рецептов

`{ "success": true, "recipes": [ { "recipe_id", "title", "is_public", "tags", "access_code", "created_at", "updated_at" } ] }` — до 200, сортировка по `updated_at` desc. Контент не отдаётся — качайте отдельно.

### 11.4. `GET /api/v1/recipes/{recipe_id}` — скачать рецепт

Публичный — кто угодно (без авторизации); приватный — только владелец (иначе `403` «Доступ ограничен автором»).

**Ответ:** `{ "recipe_id", "title", "payload_json" }` — `payload_json` строка с санитайзенным контентом (§14.1).

### 11.5. `DELETE /api/v1/recipes/{recipe_id}` — удалить свой рецепт

`{ "success": true }` или `404` «Рецепт не найден в облаке» (в т.ч. чужой — чтобы не палить существование).

### 11.6. `GET /api/v1/recipes/search?q=...&page=0&relaxed=0` — поиск публичных рецептов (авторизация)

Полнотекстовый поиск по названию/тегам публичных рецептов сообщества.

- `q` ≥ 2 символа; сервер сам нормализует: `ё→е`, отбрасывает знаки, слова < 2 символов, максимум 6 слов, русская морфология (усечение основы + префиксный поиск).
- `page` с нуля, по 20 результатов, `has_more` — есть ли следующая.
- `relaxed` в ответе: `true`, если сервер ослабил запрос (строгий AND ничего не нашёл) — дальше листайте с `relaxed=1`.
- Rate limit: **30 поисков/мин** → `429 RATE_LIMITED`.

**Ответ:** `{ "success", "page", "relaxed", "has_more", "results": [ { "recipe_id", "title", "tags", "updated_at" } ] }`

### 11.7. `GET /api/v1/recipes/public?page=0&limit=100` — публичная лента (без авторизации)

Лента сообщества, сортировка по `updated_at` desc, `limit` 1–100 (дефолт 100).

**Ответ:** `{ "success", "page", "has_more", "recipes": [ { "recipe_id", "title", "is_public", "tags", "created_at", "updated_at" } ] }`

### 11.8. `GET /api/v1/recipes/access/{код}` — скачать по коду доступа (без авторизации)

Код 10 символов; пробелы/дефисы не мешают, регистр не важен. Ответ: `{ "recipe_id", "title", "payload_json" }`. `404` «Рецепт по этому коду не найден» / «Неверный код доступа».

**Клиент:** скачанный рецепт — чистый контент (§14.1). При сохранении в локальную базу проинициализируйте личные поля дефолтами (`status: PLANNED`, `isFavorite: false`, `rating: 0`, свой `cloudId` = `recipe_id` из ответа) — иначе исключение уже установленных в ИИ-поиске не сработает.

## 12. Бэкап RecipeEntity

Слепок локальной библиотеки на сервере. Хранит **всё личное** (это backup телефона, а не общий контент). **Только последний снапшот**: каждая выгрузка полностью заменяет предыдущую. Строгая валидация — таблицу нельзя использовать как свободное хранилище. Бэкап делит «Облако» тарифа с облачными рецептами: после выгрузки суммарно (облачные + бэкап) ≤ `quotas.cloud.limit`.

### 12.1. `POST /api/v1/recipes/backup` (авторизация)

**Тело:** `{ "recipes": [ RecipeEntity, ... ] }` — контракт в §14.2.

**Ответ:** `{ "success": true, "stored": 231, "size_bytes": 812345, "created_at": 1731580800 }`

**Лимиты и ошибки:**

| Ошибка | HTTP | Условие |
|---|---|---|
| `RATE_LIMITED` «Слишком часто…» | 429 | > **6 выгрузок в час** |
| `CLOUD_QUOTA_EXCEEDED` | 403 | после выгрузки облачные рецепты + бэкап превысят «Облако» тарифа (`quotas.cloud.limit`); при 0 — «Бэкапы недоступны на вашем тарифе» |
| `INVALID_BACKUP` | 400 | валидация не прошла; текст вида `Рецепт #12: неизвестное поле "xyz"` |
| «Бэкап слишком большой (максимум ~1 МБ)» | 413 | суммарно > 1 МБ |
| (валидация) ≤ 500 рецептов, ≤ 90 КБ на рецепт | 400 | текст ошибки называет лимит |

**Клиент:**
- DTO — **только разрешённые ключи** (§14.2), строки/типы выверены (сервер отклонит `"rating": "5"`).
- Место в лимите делят облачные рецепты и бэкап: до выгрузки проверьте `quotas.cloud.limit` и число своих облачных рецептов (`GET /recipes`). Выгрузка бэкапа не больше текущего разрешена всегда — уменьшение занятого места.
- Рецептов > 500 — не отправляйте вообще: покажите честное сообщение («В базе N рецептов. Облачный бэкап поддерживает максимум 500»).
- Бэкап — best-effort: сбой синхронизации не блокирует и не откатывает локальные правки.

### 12.2. `GET /api/v1/recipes/backup` (авторизация)

Без бэкапа: `{ "success": true, "exists": false }`.
С бэкапом: `{ "success": true, "exists": true, "created_at": ..., "recipes_count": 231, "recipes": [ ...то же, что отправляли... ] }`.

Рецепты возвращаются **как были сохранены** (валидированные оригиналы, порядок сохранён). Восстановление — вставить в локальную базу как есть.

## 14. Контракты данных

### 14.1. Рецепт: локальная форма и облачная форма

**Локальная / ИИ-форма** (приходит из `/recipe/parse`, хранится локально, уходит в бэкап): полная структура из ИИ-промпта:

```json
{
  "title": "Шарлотка с яблоками",
  "prepTimeMinutes": 15,
  "cookTimeMinutes": 35,
  "servings": 6,
  "yieldUnit": "порций",
  "chefHeatingType": "Духовка (режим верх-низ)",
  "chefTemperature": "180 °C",
  "chefTiming": "35-40 мин",
  "chefReadinessSign": "Золотистая корочка, сухая зубочистка",
  "ingredients": [
    { "name": "Мука пшеничная", "amount": "160", "unit": "г", "groupName": "Для теста", "note": "просеять" }
  ],
  "steps": [
    "Взбить яйца с @[Сахар (Для теста)] миксером."
  ],
  "tags": ["Выпечка", "Яблоки"],
  "notes": "...",
  "calories": 210, "protein": 5, "fat": 4, "carbs": 39
}
```

- Ссылки на ингредиенты в шагах — строго `@[Название (Секция)]` или `@[Название]` (клиент по ним собирает группы при готовке).
- Плюс личные поля RecipeEntity (status, isFavorite, rating, postCookNote, cloudId, cloudAccessCode, createdAt, updatedAt) — их ИИ не создаёт, их ведёт клиент.

**Облачная форма** (`upload` / `GET {id}` / `access/{code}`) — whitelist: **в облаке существует только контент**:

| Поле | Тип | Кап |
|---|---|---|
| `title` | string | 200 (обязателен) |
| `description` | string | 2000 |
| `yieldUnit` | string | 30 |
| `notes` | string | 2000 |
| `prepTimeMinutes` | number | 0…10080 |
| `cookTimeMinutes` | number | 0…10080 |
| `baseServings` | number | 0…999 |
| `calories`, `protein`, `fat`, `carbs` | number | 0…100000 |
| `servingsEnabled` | boolean | — |
| `ingredients` | array | 1–150 (обязателен); элемент — строка ≤200 или объект (строки ≤200, суммарно ≤600 байт на элемент) |
| `steps` | array | 1–100 (обязателен); капы те же |
| `tags` | array | ≤30 строк |

**Вырезаются всегда:** `id`, `status`, `isFavorite`, `rating`, `postCookNote`, `chefHeatingType`, `chefTemperature`, `chefTiming`, `chefReadinessSign`, `servings`, `cloudId`, `cloudAccessCode`, `createdAt`, `updatedAt` и любые неизвестные ключи.

Сервер сам считает `ingredients_text` (по `ingredients[].name`) и `total_minutes` (prep+cook) — передавать/ожидать их в payload не нужно.

### 14.2. RecipeEntity для бэкапа — строгое множество ключей

Верхний уровень: `{ "recipes": [...] }`, каждый рецепт — объект **только из перечисленных ключей**. Все поля опциональны кроме `title`; `null` ≡ отсутствует.

| Поле | Тип/кап |
|---|---|
| `id` | number 0…1e9 |
| `title` | **string, непустая, ≤200 (обязателен)** |
| `status` | `"PLANNED" \| "VERIFIED" \| "NEEDS_WORK" \| "ARCHIVED"` |
| `isFavorite` | boolean |
| `servingsEnabled` | boolean |
| `rating` | целое 0–5 |
| `postCookNote` | string ≤2000 |
| `chefHeatingType` | string ≤100 |
| `chefTemperature` | string ≤20 |
| `notes` | string ≤2000 |
| `description` | string ≤2000 |
| `cloudId` | string ≤120 |
| `cloudAccessCode` | string ≤20 |
| `prepTimeMinutes`, `cookTimeMinutes` | number 0…10080 |
| `baseServings` | number 0…999 |
| `calories`, `protein`, `fat`, `carbs` | number 0…100000 |
| `createdAt`, `updatedAt` | number ≤1e13 (Unix-миллисекунды) |
| `ingredients`, `steps`, `tags` | массивы (каждый ≤60 КБ в JSON) |

Неизвестное поле → `400 INVALID_BACKUP` с именем поля и номером рецепта. Лимиты: ≤500 рецептов, ≤90 КБ JSON на рецепт, ≤1 МБ суммарно, 6 выгрузок/час, и «Облако» тарифа — общий котёл с облачными рецептами (`cloud_recipe_quota`).

## 16. Рекомендуемые сценарии клиента

### 16.1. Холодный старт

1. `GET /app/config` (кэш → офлайн) → проверить `maintenance_active`, `min_version_code`, загрузить `ai_costs`.
2. Нет `session_token` → `POST /auth/init`.
3. `GET /user/status` → закэшировать квоты/тариф/расценки.
4. Любой 401 → новый `auth/init` → повтор запроса (один ретрай).

### 16.2. ИИ-поиск: выбор flow

- Библиотека ≤ 60–120 рецептов → обычный поиск (один запрос).
- Библиотека больше или важна экономия лимита → двухфазный: суммарно 1 «витамин ИИ» независимо от размера библиотеки.
- Прогноз цены обычного поиска ДО запроса: `max(1, ceil(N/60)) × ai_costs.search_single_per_60`.

### 16.3. Синхронизация квот

После любого платного ответа обновляйте кэш квоты из `cost`/`remaining_month`. `/user/status` — только на старте, после активации ключа и после ошибок квоты.

### 16.4. Правила безопасности данных

- В облако (`upload`) — только контент; «спрятать» личные поля в payload нельзя (вырежут).
- В бэкап — всё, включая личное, но только разрешённые ключи и типы.
- `cloudId` локального рецепта = `recipe_id` облака (устанавливайте при скачивании) — иначе исключение уже установленных в ИИ-поиске не сработает.

## 17. Доступ и безопасность

Панель Cookin Studio открывается по секретному пути `https://cooking.aetnox.workers.dev/admin/{admin_panel_slug}` (slug хранится в `app_config.admin_panel_slug`; без совпадения — 404).

REST-часть — `https://cooking.aetnox.workers.dev/api/v1/admin/*` с заголовком **`X-Admin-Secret`**:

- Секрет задаётся **только** переменной окружения `ADMIN_SECRET` (Cloudflare Secret, не в БД). Если не задан или короче 16 символов — весь `/api/v1/admin/*` отвечает `503`.
- Неверный секрет → `403` «Доступ запрещен. Неверный пароль администратора». **10 неудачных попыток с одного IP → блокировка на 5 минут** (`429 ADMIN_LOCKED`); успешный вход снимает блок.
- Все не-GET запросы (кроме SQL-консоли) пишутся в журнал аудита `admin_audit` (просмотр: `GET /admin/audit`, панель — вкладка «🧾 Логи»).
- Ошибки админских эндпоинтов могут содержать `details` в 500 — это норма (админ видит больше, чем клиент).

## 19. Метрики ИИ

### `GET /admin/stats/ai`

| Блок | Содержимое |
|---|---|
| `today` | вызовы/успехи/средняя латентность/tokens за сегодня |
| `by_model_7d[]` | по моделям: `attempts`, `successes`, `success_rate`, `prompt_tokens`, `completion_tokens`, `avg_latency_ms`, `last_error_at`, `cost` ($ за 7 дней), цены `cost_p`/`cost_c` |
| `by_feature_7d[]` | по функциям (`recipe_parse`, `assistant_step`, `recipe_ai_search`, `admin_assistant`): успешность, латентность, токены, **p50/p95 латентности** |
| `by_phase_7d` | счётчики вызовов модели: `two_phase_calls`, `plan_calls` (meta «двухфазный: план»), `finish_calls` («двухфазный: финал»), `assistant_steps`, `parse_calls` — **так отслеживается миграция клиентов на двухфазный поиск** |
| `latency_percentiles` | `{feature: {p50, p95, samples}}` |
| `top_users_7d[]` | топ-20 аккаунтов по токенам за 7 дней + их месячные счётчики `ai_month`/`quota` |
| `daily_14d[]` | дневной ряд: вызовы, ok, токены, латентность, `cost` ($) |

**Оценка стоимости**: `cost = prompt_tokens/1e6 × cost_per_1m_prompt + completion_tokens/1e6 × cost_per_1m_completion` — цены задаются у каждой модели в панели (§23). Пока цены 0 — `cost` показывает 0.

### `GET /admin/stats/ai-live`

Запросы, выполняющиеся прямо сейчас (таблица `ai_live_requests`, чистка записей старше 180 сек): `{now, live[{request_id, feature, detail, model_id, model_name, rank, status, status_text, attempt, started_at, updated_at}]}`. Статусы: `start` → `waiting` → (retrying) → успех (запись удаляется) / `fallback`.

## 20. Логи ИИ-запросов

- **`GET /admin/logs?limit=200&feature=&status=&hours=168`** — `{total, older_24h, logs[]}`. Фильтры: `limit` 1–500 (дефолт 200), `feature` (точное имя), `status` `ok|err`, `hours` 1–8760 (дефолт 168). Каждая запись: `created_at, feature, model_id, rank, success, latency_ms, error, prompt_tokens, completion_tokens, account_id, detail` (сниппет запроса ≤200), `meta` ≤2000 (шаг цикла + **tool-вызовы с аргументами** + сниппет ответа модели).
- **`DELETE /admin/logs?hours=24`** — удалить все логи старше N часов (1–8760, дефолт 24): `{success, deleted, hours}`.

## 21. Тарифные планы (квоты)

- **`GET /admin/plans`** — все тарифы с полями ниже.
- **`POST /admin/plans`** — upsert: `{plan_level, name, monthly_ai_quota, max_history_turns, allow_photos, max_agent_depth, max_rank, monthly_photo_quota, cloud_recipe_quota}`. Легаси: если `monthly_ai_quota` не прислан, но есть старые суточные `daily_recipe_quota`/`daily_assistant_quota` — они конвертируются (сумма × 30).
- **`DELETE /admin/plans/{level}`** — план 0 (Карантин) системный, удалить нельзя (`400`).

### Поля тарифа — это вторая половина «лимитов»

| Поле | На что влияет |
|---|---|
| `monthly_ai_quota` | Месячный лимит «витаминов ИИ» (весовая система §4.2). `0` → `ASSISTANT_LOCKED` / `AI_SEARCH_LOCKED` |
| `monthly_photo_quota` | Месячный лимит фото-оцифровок. `0` → фото недоступно |
| `cloud_recipe_quota` | Общий котёл облачного хранения: облачные рецепты + рецептов в бэкапе суммарно ≤ этой цифры (§12). `0` → upload новых и выгрузка бэкапа отклоняются (`CLOUD_QUOTA_EXCEEDED`) |
| `max_history_turns` | Пары сообщений диалога: ассистент шлёт `×2` последних сообщений; ИИ-поиск — дефолт 3 пары (при 0 берётся дефолт, а у ассистента останется 1 сообщение) |
| `allow_photos` | Разрешена ли оцифровка по фото (`PHOTO_RESTRICTED`) |
| `max_agent_depth` | Число tool-раундов ИИ-поиска на один запрос (эффективно 1–3, сервер капает); видно клиенту в `/user/status` |
| `max_rank` | Максимальный ранг модели каскада для этого тарифа. `0` = ИИ недоступен; ключи генерируются только на тарифы с `max_rank > 0` |

> **Уровень 0 — блокирующий план.** Сервер проверяет уровень 0 **до** всех квот: на нём весь ИИ закрыт (`FREE_TIER_QUARANTINE`) независимо от того, что записано в полях плана (число в `monthly_ai_quota` у уровня 0 — просто данные в БД, сервер их не применяет). Из полей уровня 0 реально действует только `cloud_recipe_quota` (он нулевой: загрузка в облако и выгрузка бэкапа отклоняются; скачивание, чтение и уже сохранённый бэкап работают). На уровень 0 попадают устройства после переноса подписки (30 дней блокировки) и аккаунты, выставленные админом вручную; новые и истёкшие пользователи получают уровень 1.

## 22. Провайдеры ИИ

- **`GET /admin/providers`** — список **без секретов**: `api_key: ""`, вместо этого `has_key`, `key_hint` («…abcd»).
- **`POST /admin/providers`** — upsert: `{id, name, provider_type: gemini|openai|anthropic, base_url, api_key, is_active}`. Пустой `api_key` сохраняет прежний ключ.
- **`POST /admin/providers/inspect`** — `{id}` → проверка связи и список моделей провайдера (до 200): `{ok, status, latency_ms, count, models[]}` или `{ok: false, latency_ms, error}`.
- **`DELETE /admin/providers/{id}`**.

В панели провайдера можно выключить/включить кнопкой (is_active) без удаления — выключенный провайдер выпадает из каскада вместе со всеми своими моделями.

Изменения провайдеров/моделей инвалидируют кэш каскада мгновенно на этом инстансе (полный TTL 60 сек — до минуты состав может отдаваться старый на других инстансах).

## 23. Модели ИИ и каскад

- **`GET /admin/models`** — все модели с именем/типом провайдера.
- **`POST /admin/models`** — upsert: `{id, provider_id, model_name, rank, priority=1, is_active=1, supports_reasoning, supports_tools=1, cost_per_1m_prompt=0, cost_per_1m_completion=0, features}`.
  - `features` — массив категорий: `recipe_parse`, `assistant_step`, `recipe_ai_search`, `admin_assistant`. Пусто или все 4 → `'all'` (модель годится для всего).
  - `supports_tools` — участвует ли модель в шагах с function calling (🛠 в панели). Модели без tools на tool-шагах **пропускаются каскадом**.
  - `cost_per_1m_prompt` / `cost_per_1m_completion` — цены $ за 1М токенов для оценки стоимости (§19).
- **`POST /admin/models/test`** — `{id}` → пробный «ping»-запрос генерации: `{ok, status, latency_ms, preview|error}`.
- **`DELETE /admin/models/{id}`**.

### Как работает каскад (важно при настройке)

1. Активные модели группируются по `rank` (выше rank = «дороже/лучше»), внутри ранга сортируются по `priority` (меньше = раньше).
2. Для вызова берётся целевой ранг (клиент: `plan.max_rank` тарифа) и стратегия **`fallback_down`**: целевой ранг → вниз к рангу 1. Другие стратегии (`exact`, `fallback_up`, `nearest`) используются админ-ассистентом.
3. Модель пропускается, если: неактивна; `supports_tools = 0` на шаге с инструментами; её `features` не содержит нужную категорию; она в cooldown.
4. Cooldown: модель, вернувшая 404/429/503, исключается на **60 секунд** (кэш в памяти инстанса).
5. Транзиентные ошибки (429/500/502/503/504, timeout, network) → **1 повтор** через 700 мс на той же модели, затем переход к следующей.
6. Каждый вызов логируется в `ai_request_logs` (§20); на клиент уходит только общий текст ошибки — никогда имя модели/ранг.

## 28. SQL-консоль и аудит

- **`POST /admin/sql`** — `{ "query": "SELECT ..." }` → `{success, results, meta}`. По умолчанию **только чтение** (SELECT/WITH/EXPLAIN/PRAGMA table_info|table_list); запись открывается переменной окружения `ADMIN_SQL_WRITE=1`. В результатах `api_key` маскируется (`***`). ## 29. Админ-ассистент

Полноценный ИИ-агент управления проектом (SSE-стриминг, инструменты, подтверждение write-действий человеком).

### Сессии

- **`GET /admin/assistant/sessions`** — 50 последних.
- **`GET /admin/assistant/sessions/{id}`** — `{session, messages (до 200), actions (ожидающие подтверждения)}`.
- **`DELETE /admin/assistant/sessions/{id}`** — удалить сессию с историей.

### Чат: `POST /admin/assistant/chat`

**Тело:** `{message (обязателен), session_id?, target_rank? (дефолт 2), rank_strategy? (fallback_down|exact|fallback_up|nearest), reasoning_level? (off|low|medium|high, дефолт medium), max_steps? (1–8, дефолт 5)}`.

**Ответ — поток SSE**, события по порядку:

| Событие | Содержимое |
|---|---|
| `session` | `{session_id, target_rank, rank_strategy, reasoning_level}` |
| `status` | `{step, text}` — прогресс |
| `model_event` | `{type: "model_attempt"|"model_error", model_id, model_name, rank}` — перебор каскада |
| `tool_call` | `{step, id, name, args, mode: "read"|"write"}` |
| `tool_result` | `{step, id, name, ok}` |
| `pending_action` | `{action_id, tool_name, args, summary, status: "pending"}` — write-действие в очереди |
| `message` | `{role: "assistant", content, used_model, used_rank, reasoning_level, pending_actions[]}` — итог |
| `done` | `{session_id, steps_used}` |
| `error` | `{error}` |

Read-инструменты выполняются сразу; write-инструменты **только ставятся в очередь** — модель подтверждает их вызов, но исполнение происходит после подтверждения человеком.

### Инструменты ассистента

- **Read (авто):** `get_project_overview`, `get_stats_users`, `get_stats_ai`, `get_stats_subscriptions`, `list_accounts`, `list_plans`, `list_models_and_providers`, `list_feedback`, `list_recipes`, `list_keys`, `get_audit_log`, `test_model`, `run_readonly_sql`.
- **Write (подтверждение):** `update_account`, `delete_account`, `upsert_plan`, `delete_plan`, `upsert_provider`, `delete_provider`, `upsert_model`, `delete_model`, `generate_keys`, `delete_key`, `delete_recipe`, `delete_feedback`, `set_app_config` (кроме `admin_panel_html`/`admin_panel_slug`).

### Подтверждение действий

- **`POST /admin/assistant/actions/{action_id}/confirm`** — исполнить (повторное подтверждение уже обработанного → `409`).
- **`POST /admin/assistant/actions/{action_id}/reject`** — отклонить.

> Нюанс: write-инструмент `upsert_model` умеет менять только базовые поля + `supports_reasoning` — флаги `supports_tools`, `features` и цены задавайте через `POST /admin/models` (§23) или панель.
